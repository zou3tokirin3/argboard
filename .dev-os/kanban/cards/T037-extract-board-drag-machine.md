## 目的

[board.tsx](../../../ui/board.tsx) の `BoardView` は **633行の単一関数**（473–1106行）で、
pan / node / link の3状態ドラッグ機械と全JSXが同居している。

T031–T033 パケット §6 が見積もりリスクとして
「`board.tsx` は既に1,106行で drag 状態機械が3種ある。**ここが膨らみやすい**」と自ら挙げた場所。
T032 の矩形選択（`type:"marquee"`）は**4つ目の状態**をここに足す設計になっており、
その前に分けておかないと、次に触る者が633行を読み切ってから手を入れることになる。

**行数はほぼ減らない。** 目的は次に膨らむ理由を消すこと。

## T036 から分離した理由

T036（アイコンJSXと誕生イベントの重複畳み・約 −110行）と同時にやると、
**壊れたときに何が原因か切り分けられない**。本カードが触るのは:

- **T014 の付箋ノリドラッグ** — T031–T033 パケット §6 が「最大の注意点」に挙げた挙動
- 実ポインタードラッグは §10-3 の方針により **smoke 1本ぶんしか生存確認がない**
  （残りはテストフック経由で、同じ関数を呼ぶが pointer イベントの経路は通らない）

つまりこの領域は、機械検証の網が最も粗い場所。純関数とJSXの整理（T036）とは
リスクの質が違うので、独立したコミット単位にする。

## 対象（現物確認・2026-07-25）

`BoardView` 内に定義されている関数:

| 塊 | 関数 | 行数目安 |
|---|---|---:|
| 座標・当たり判定 | `clientToWorld` / `hitNode` | 約45 |
| ポインタ入口 | `onCanvasPointerDown` / `onPaperPointerDown` / `onAdhesivePointerDown` / `onThreadPointerDown` | 約75 |
| ポインタ進行・確定 | `onPointerMove` / `onPointerUp` | 約75 |
| ホイール・ドロップ | `onWheel` / `onDragOver` / `onDrop` | 約50 |
| 派生値・JSX | 上記以外すべて | 約390 |

状態は `dragRef: Drag | null`（`pan` / `node` / `link` の3ヴァリアント）と
`rubber: Rubber | null` の2つ。

## やること

1. `useBoardDrag()` フックを切り出す。`dragRef` / `rubber` / 上記ハンドラ群を持ち、
   `BoardView` へはハンドラと `rubber` だけを返す
2. リプレイバー（約100行のJSX）と視点フロート（約90行のJSX）をコンポーネントへ分ける。
   **T036 の `IconButton` が入った後に行う**（先にやると同じJSXを2回書き換えることになる）
3. **ready 確定: `board.tsx` 1ファイルに残す**（本体ファイル数13・警告基準15。
   新規ファイルを増やさない。フック／コンポーネントは同ファイル内の関数として切り出す）
