## 目的

保守性と拡張性のためのリファクタリングを検討する探索カード。**本カードでは実装しない。**
検討の結果を、小さく分けた実装カード（1枚1テーマ・各回で check/test/smoke 緑）へ切り出す。

軸は1つ: **同じカードの同じ項目を書く道が、画面ごとにばらばらにある**こと。
これがそのまま、上書きで入力が消えるバグ（T083）の原因になっている。将来の共同編集（Durable Objects・
移行プラン §6）では「書く道が1本」であることが同期の前提になるので、その前に形を決めておく。

出典: 2026-10-20 人間「これを機会に保守性と拡張性を考えたリファクタリングを検討するチケットを切ってみるのも良いかな」
（T064 の作り直し中に、保存の道が2本あるとメモが消えるバグを見つけたことが発端）

## 背景（現物確認・2026-10-20・`task/T064` 時点）

### 1. カードの項目を書く道がばらばら（最優先）

| 書き手 | 下書きの持ち方 | 保存 |
|---|---|---|
| インスペクタ（`inspector.tsx`） | 自前 `useState`（title/body/url/storyWhen/storyUntil） | debounce 400ms ＋選択が変わるとき**全項目**を保存 |
| 発見ログのタイトル直し（T053・`stream.tsx` `StreamCardTitle`） | 自前 `useState` | debounce 400ms で `updateCard` |
| 拡大表示のメモ（T064） | 作り直しでインスペクタの下書きに相乗り（道は増やしていない） | — |

- インスペクタは**カードが切り替わったときしか下書きを読み直さない**。選択が外れるときに古い下書きで全項目を書き戻す。
  → ほかの道で書いた内容が消える（**T083 で実害を確認済み**）
- `updateCard` は title/body/url を必ず全部受け取る形。「変えた項目だけ送る」ができない

### 2. `state.ts` が大きい
- 1,730行・export 124個・signal 25個。保存・選択・掘り中・拡大・メディア・リプレイが同居
- 触るたびに全体を読む必要がある。T037（board のドラッグ状態機械の切り出し）と同じ型の問題

### 3. 同じ形のコードが複数ある
- 画像 URL の取り出しは T064 で `useMediaUrl` に寄せた（4か所 → 1か所）。同じ型の重複が他にもないか棚卸しする
- Esc の処理が `main.tsx`・`stream.tsx`・`inspector.tsx`・`image-overlay.tsx` に分散。優先順位（どれが先に閉じるか）が暗黙
- 発見ログのサムネ周り（`stream.tsx`）が、編集可／不可の2分岐で同じJSXを持っている

## 検討すること（この順で）

1. **カードの下書きを誰が持つか**
   - 案A: インスペクタが持ち、ほかの画面は相乗り（T064 の形）。小さいが、インスペクタが無い画面では使えない
   - 案B: カード単位の下書きストア（signal）を1つ作り、全画面が読み書きする。保存も1か所
   - 案C: 下書きを持たず、入力ごとに「変えた項目だけ」を即保存（`updateCard` を部分更新にする）
   - 判断軸: バグの消え方／行数／共同編集（イベント単位の同期）との相性
2. **`updateCard` を部分更新にするか**（`card_updated` イベントの形にも効く・リプレイ互換を確認）
3. **`state.ts` の分け方**（責務ごとのファイル分割。Store 契約 §6 には触らない）
4. **Esc の優先順位を1か所で決めるか**
