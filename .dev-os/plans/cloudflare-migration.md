## 0. 目的とゴール

1. ビルド・開発・検証のループを Deno から外す
2. 公開は Cloudflare に一本化する
3. 将来の共同編集に向けて、Durable Objects（DO）が載る土台を先に整える

**変えないもの**: ブラウザ内保存（IndexedDB）、静的配信、Project JSON 契約（version 付き）、
`ui/db.ts` の Store 契約。共同編集を入れるまで、データはこれまでどおりブラウザの中にだけある。

## 1. 現状の Deno 依存（棚卸し）

| 場所 | 何に使っているか | 移行の重さ |
|---|---|---|
| `deno.json` tasks | dev / build / check / test / smoke / budget / cf:dev | 中（タスク定義を置き換える） |
| `deno bundle` | `ui/main.tsx` → `dist/bundle.js` | 中（バンドラを選ぶ） |
| `deno fmt` / `deno lint` / `deno check` | check ループ | 中（代替ツールを選ぶ） |
| `deno test`（`tests/unit/*.test.ts` 20本前後） | unit | 軽〜中（`Deno.test` の呼び方と assert を置き換える） |
| `@astral/astral`（`tests/smoke.ts`） | スモークE2E 5本 | 中（Playwright へ。PLAN §13 に乗り換え先として記載済み） |
| `serve.ts` | dev サーバー（`Deno.serve`） | 軽（Vite の dev か wrangler dev に置き換わる） |
| `tools/budget.ts` | flow ゲート計測（`Deno.Command` など） | 中（Node 向けに書き直す。ゲートの正本なので落とせない） |

## 3. フェーズA: 調査と選定（実装なし）

決めること（各1枚の短い比較メモで足りる）:

| 論点 | 候補 | 判断軸 |
|---|---|---|
| パッケージ管理・実行 | Node + **pnpm**（ユーザー規約で pnpm 固定） | mise で Node を固定 |
| バンドラ／dev サーバー | **Vite**（Preact プラグイン） / esbuild 単体 | 依存の少なさ（PLAN §11-7）。esbuild 単体が最小。Vite は dev 体験が良い |
| unit | **Vitest** / `node:test` | 依存の少なさ。`node:test` なら追加依存ゼロ |
| スモークE2E | **Playwright**（PLAN §13 記載済み） | 5本上限・flaky 即削除の規律はそのまま |
| fmt / lint | Biome（1本で両方） / Prettier + ESLint | 依存を最小に。Biome 1本が軽い |
| 型チェック | `tsc --noEmit` | `.ts` 拡張子 import を許す設定（`allowImportingTsExtensions`）が要る |
| Deno 本体の延命 | コミュニティ継続なら残す選択肢もある | 公式サポート前提は置かない（§14 改訂30） |

**私の推し**（採択は人間）: Node + pnpm + esbuild（または Vite）+ `node:test` + Playwright + Biome。
Preact + signals 以外の依存を増やさない原則（§11-7）に最も近い組み合わせ。

成果物: `.dev-os/kanban/packets/T081-a.md`（選定の評価パケット）。依存が増えるので、パケットで人間GOを取る。

## 4. フェーズB: ツールチェーン置き換え

**鉄則: 1カード1置き換え。その時点で必ず check→test→smoke が緑に戻ること。**
全部まとめて一気に差し替えない（前作の「ループが本流を止めた」失敗の再発防止）。

| 順 | 子カード案 | 内容 | 緑の定義 |
|---|---|---|---|
| B1 | build を新バンドラへ | `dist/` が同等に出る。`deno bundle` と並走で差分比較 | smoke 緑（旧ランナーのまま） |
| B2 | dev サーバー | `serve.ts` を置き換え。ブランチ名をタイトルに出す機能は維持 | 手元で開ける |
| B3 | unit を Node へ | `Deno.test` → `node:test`。assert を置き換え | unit 全本緑 |
| B4 | smoke を Playwright へ | 5本を移す。`?test=1` フックは維持 | smoke 5本緑 |
| B5 | fmt / lint / 型 | Biome + tsc。既存コードの整形差分は**1コミットに隔離** | check 緑 |
| B6 | `tools/budget.ts` を Node へ | 計測の定義（PLAN §4）は変えない。移行前後で同じ数字が出ることを確認 | 同一コミットで旧新の値が一致 |
| B7 | CI と mise | `pages.yml` と `mise.toml`、BOOTSTRAP を更新。`deno.json` を削除 | CI 緑 |

注意:
- **B6 は慎重に。** budget はゲートの正本。旧実装と新実装を同じコミットに当てて、数字が一致してから切り替える。
  一致しない指標は、定義が変わるので PLAN §4 の改訂（人間判断）に回す
- B5 の整形差分が `--since main` の行数計測を汚す。**整形コミットは別カード・別 PR**にして、計測の基準点を引き直す
- `deno.lock` は B7 で削除。`pnpm-lock.yaml` を導入

## 5. フェーズC: Cloudflare 一本化

現状: GitHub Pages と Cloudflare Workers 静的アセット（`wrangler.jsonc`）の**二重運用**。

| カード案 | 内容 |
|---|---|
| C1 | 配信を Cloudflare に一本化。GitHub Pages の workflow を止めるかは人間判断（旧URLの扱いが要る） |
| C2 | `wrangler deploy` を CI に載せる（`CLOUDFLARE_API_TOKEN` を GitHub Secrets へ。**トークンの発行と登録は人間が行う**） |
| C3 | `deno task cf:dev` を新ループの `dev` に統合（`wrangler dev` で本番に近い形で確認） |

## 6. フェーズD: Durable Objects（共同編集の土台）

PLAN §12 の「共同編集・同期・クラウド保存・アカウント」は **Won't のまま**。
ここは「入れる」ではなく「入れるときの形を先に決めておく」ための設計メモ。着手には Won't 解除のパケットが要る。

### 6-1. なぜ DO か

- 1プロジェクト = 1 DO にすると、同じプロジェクトを開く全員が同じ DO に集まる。順序づけが自然に決まる
- WebSocket のハイバネーションと SQLite 内蔵ストレージ（DO の SQLite バックエンド）が使える
- 画像 Blob は DO ではなく R2 に置く（現行の `media` ストアと同じ分離）

### 6-2. 既存設計との接点（ここが強み）

| 既存 | DO 化したときの意味 |
|---|---|
| `ui/db.ts` の Store 契約（§6） | 差し替え点は引き続きこの1枚。`DoStore` を足して選べるようにする |
| `events`（append-only 操作ログ・T024） | **そのまま同期の単位にできる。** 全置換ではなく「イベントを送る」形に寄せられる |
| `foundAt` / `foundVia`（不変フィールド） | 衝突しない。作成時に確定し、以後書き換わらない |
| 糸・カードの削除 | 競合しやすい。イベントの順序を DO が決めれば足りる（CRDT なしで始められる可能性） |
| 画像は media id 参照 | R2 のキーにそのまま使える |

### 6-3. 決めておくこと（先送りしてよいが、忘れない）

1. **同期モデル**: DO が順序を決める単純なイベント列（推し）か、CRDT か。単純なほうから始める
2. **認証**: アカウントなしで始めるなら「推測不能な URL を知っている人だけ」の共有リンク型。Won't（アカウント）に触れない
3. **ローカルファースト維持**: オフラインで書けて、戻ったら送る。現行の「ブラウザの中に残る」を壊さない
4. **料金と上限**: DO の請求（リクエスト・duration・ストレージ）。無料枠の範囲で動くかを実測してから決める
5. **プライバシー表記**: README の「データは外部へ送信せず」が**嘘になる**。共同編集を有効にしたプロジェクトだけ、明示オプトインにする。既定は今のまま

### 6-4. D の入口条件

- A〜C が完了している
- 実プレイで「複数人で同じ ARG を追いたい」が観測されている（§11-5）
- Won't 解除の評価パケットに人間GOが出ている
